# AGENTS.md — CONSTRUPRE Website Modernization

## 1. Mission

You are working on the website of **CONSTRUPRE (Construcciones Prefabricadas)**, an El Salvador construction company focused on prefabricated construction.

Your goal is **not merely to make the website prettier**. The goal is to turn the existing site into a modern, credible, fast, responsive and conversion-oriented website while preserving the company's real content, project history and technical credibility.

The starting files may come from an **HTTrack mirror of the public website**. Treat them as a public frontend snapshot, not as the original server source code.

## 2. Source-of-truth rules

Use this priority order when deciding what is true:

1. The files in the local project/mirror.
2. Content already present in the original CONSTRUPRE public website.
3. This `AGENTS.md` business context.
4. Reasonable UX or implementation decisions that do not create new factual claims.

Never invent business facts just to fill a design.

Do **not** invent or assume:

- prices or price ranges;
- construction times;
- guarantees;
- certifications;
- awards;
- client names;
- testimonials;
- financing plans;
- promotions;
- exact number of completed projects unless derived from the local data;
- exact current years of experience beyond the wording already published by the company;
- WhatsApp numbers or email addresses that are not verified in the source files;
- backend capabilities that do not exist in the mirror.

If information is uncertain, preserve the original wording or leave it out.

## 3. Business context

### Brand

**CONSTRUPRE** / **Construcciones Prefabricadas**

The company presents itself as:

- 100% Salvadoran;
- experienced in the prefabricated construction market;
- focused on service, quality and professionalism;
- capable of fabrication, design and construction;
- oriented toward personalized projects based on the client's needs, ideas and goals.

The existing company copy states **“Más de 24 años de experiencia”**. Preserve this statement if needed, but do not automatically convert it to a larger number based only on the current calendar year.

The company also mentions Christian values in its institutional description. Keep that information in an appropriate company/about section when relevant, but it does not need to dominate the visual identity.

### Core value proposition

CONSTRUPRE should feel like an established construction company that can take a customer's idea and turn it into a practical, customized prefabricated construction project.

The website should communicate:

- experience;
- construction know-how;
- personalization;
- solidity and durability;
- practical/economic value;
- attractive finishes;
- real completed work;
- trust.

Do not position the company merely as a seller of “cheap prefab houses”.

The company's actual portfolio includes a wider range of work such as houses, apartments, terraces, cabins, warehouses, offices, recreational projects, retaining/perimeter solutions and related construction work.

Do not design the information architecture as if CONSTRUPRE only builds houses.

## 5. Technical credibility

The existing services page states that CONSTRUPRE's prefabricated elements are made with:

- high-strength concrete rated at **210 kg/cm²**;
- structural reinforcement using **grade 70 steel bars**.

These are useful trust-building details and can be surfaced in a section about the construction system, materials or quality.

Do not add new engineering claims, certifications or structural guarantees that are not present in the source material.

### Portfolio requirements

Before redesigning the portfolio:

1. Recursively inspect the mirror.
2. Identify every project page.
3. Identify project categories.
4. Identify and map project images to their project pages.
5. Detect duplicate titles/pages and HTTrack naming artifacts.
6. Preserve the original project content.
7. Build a structured inventory before large-scale refactoring.

Do not replace the real portfolio with a handful of generic cards or stock photos.

Prefer the company's real project photographs as the main visual language.

### Recommended project UX

A modern project listing should support:

- responsive image grid;
- clear categories/filters when technically appropriate;
- useful project titles;
- consistent image ratios without destructive cropping;
- fast loading and lazy loading;
- a clear path to individual project details.

An individual project page should ideally include:

1. strong hero image;
2. project name;
3. category;
4. area in m² when available;
5. image gallery;
6. concise project description or summary based on source content;
7. structured technical specifications;
8. related projects when data allows;
9. call to action to contact/request a quote.

Do not dump technical specifications into one unreadable paragraph. Group and label them clearly.

## 7. Target users

Design primarily for people in El Salvador who may:

- own land and want to build;
- be evaluating prefabricated construction;
- want a basic house or a house with finishes;
- need a perimeter wall/tapial;
- want a country, beach or mountain property;
- need a ranch, terrace or recreational structure;
- require a customized construction solution;
- be comparing construction options before contacting a provider.

Also account for commercial/institutional use cases because the portfolio includes non-residential work.

The audience should not need construction expertise to understand the site.

## 8. Website goals

The redesigned site must help a visitor quickly answer:

- What does CONSTRUPRE build?
- Why should I trust this company?
- What does its prefabricated construction system look like?
- What real projects has it completed?
- Can it customize a project to my needs?
- How do I contact the company or request a quote?

Primary goals:

1. Improve perceived trust and professionalism.
2. Make real completed projects easy to discover.
3. Explain services clearly.
4. Explain technical quality without overwhelming non-technical users.
5. Increase qualified contact/quote inquiries.
6. Provide an excellent mobile experience.
7. Preserve important historical/project content.
8. Improve SEO, accessibility and performance.

## 9. Visual direction

The design should feel:

- architectural;
- contemporary;
- professional;
- solid;
- clean;
- warm;
- trustworthy;
- premium but accessible.

It should **not** look like a generic SaaS/startup template.

Avoid unnecessary use of:

- neon colors;
- excessive gradients;
- glassmorphism;
- futuristic UI;
- giant decorative icons;
- generic stock illustrations;
- excessive animation;
- oversized marketing typography that hides actual project content.

Use real construction photography as the primary visual asset.

Inspect the existing logo, colors and assets before defining a new design system. Modernize the existing identity rather than arbitrarily replacing the brand.

Subtle references to concrete, wood, steel, architecture or construction geometry are acceptable when they support the content rather than becoming decoration for its own sake.

## 12. Copywriting

Write in natural, professional Spanish appropriate for El Salvador/Central America.

Tone:

- professional;
- straightforward;
- warm;
- credible;
- technically informed without unnecessary jargon.

You may improve spelling, grammar, hierarchy and readability, but preserve the factual meaning of the original content.

Avoid generic marketing filler such as:

- “redefiniendo el futuro”;
- “innovación que transforma”;
- “experiencias únicas”;
- unsupported claims such as “líderes absolutos” or “la mejor empresa”.

Prefer concrete messages backed by the portfolio and technical information.

## 13. HTTrack / legacy mirror handling

Assume the starting directory may contain files created by HTTrack, including:

- `hts-cache/`;
- HTTrack-generated `index.html`;
- downloaded HTML versions of PHP pages;
- filenames containing query-string artifacts;
- rewritten relative links;
- duplicate resource directories;
- external assets cached locally;
- broken or partially downloaded links.

The mirror does **not** imply access to:

- original PHP source code;
- MySQL database;
- admin panel;
- server configuration;
- mail server;
- private APIs;
- authentication logic.

Never pretend those systems exist.

If a form has no working backend, implement it as a clearly frontend-only form or preserve the existing endpoint without claiming successful submission. Do not create fake success behavior that can mislead the site owner.

## 14. Technical approach

### Before coding

First inspect the project and report:

- top-level file structure;
- HTML/PHP-mirror pages found;
- CSS and JS files;
- image directories and approximate asset counts;
- project pages and categories;
- external dependencies;
- broken links/assets;
- duplicate content;
- encoding problems;
- HTTrack-specific artifacts;
- current responsive behavior;
- current SEO/accessibility issues.

Then propose a concise implementation plan.

### Framework policy

Do not introduce React, Next.js, Vue, Astro, Tailwind or any other framework merely because it is modern.

If the site can be rebuilt cleanly using semantic HTML, modern CSS and lightweight JavaScript, that is a valid and often preferred solution—especially if the user wants it to run directly with VS Code Live Server.

If a framework provides a concrete benefit for managing the large project portfolio, explain the benefit before restructuring the project.

When a `package.json` or existing build system is present, inspect it before choosing commands or dependencies.

### Preserve assets

Do not delete original project images or source content during early refactoring.

If restructuring:

- preserve originals until migration is verified;
- use deterministic filenames;
- avoid unnecessary duplicate images;
- generate optimized derivatives rather than destroying source files.

## 15. Frontend standards

Prefer:

- semantic HTML5;
- accessible navigation;
- CSS custom properties/design tokens;
- responsive layout with Grid/Flexbox;
- mobile-first breakpoints;
- modular/reusable components or partials when the chosen stack supports them;
- minimal JavaScript;
- progressive enhancement;
- meaningful image alt text;
- keyboard-visible focus states;
- accessible labels on form fields;
- logical heading hierarchy;
- buttons for actions and anchors for navigation;
- reduced-motion respect for users who request it.

Avoid:

- inline styles unless necessary;
- repeated hard-coded values that should be tokens;
- JavaScript for layout tasks CSS can solve;
- massive libraries for trivial interactions;
- hover-only interactions that fail on touch devices.

## 16. Performance

The site is image-heavy, so image handling matters.

Implement where appropriate:

- responsive `srcset`/sizes;
- modern optimized formats when a safe conversion workflow exists;
- lazy loading below the fold;
- explicit image dimensions/aspect ratios to reduce layout shift;
- appropriately sized thumbnails for portfolio grids;
- minimal blocking JavaScript;
- optimized font loading;
- preservation of high-quality source images.

Do not reduce project photography to visibly poor quality just to improve a synthetic score.

## 17. SEO

Prioritize natural relevance for searches such as:

- casas prefabricadas El Salvador;
- construcción prefabricada El Salvador;
- casas prefabricadas;
- tapiales prefabricados;
- construcción en El Salvador.

Use:

- unique page titles;
- useful meta descriptions;
- one clear H1 per primary page;
- semantic headings;
- descriptive alt text;
- clean internal links;
- canonical URLs when the deployment architecture is known;
- Open Graph metadata where appropriate;
- structured data only when it accurately describes the business/content.

Do not keyword-stuff.

## 18. Project-data normalization

If many legacy project pages repeat the same markup, consider extracting project content into structured data before rebuilding the UI.

Possible normalized fields:

```text
id
slug
title
category
area_m2
location
summary
images[]
specifications[]
additional_works[]
legacy_url
```

Only populate fields from verifiable source content. Do not infer a location merely from a project title unless that interpretation is unambiguous and useful.

If normalization is performed, create a validation method to ensure no project or image was silently lost.

## 19. Forms and conversion UX

A quote/contact form may include fields such as:

- Nombre;
- Teléfono;
- Correo;
- Tipo de proyecto;
- Mensaje.

Keep it short.

Do not require unnecessary personal data.

If no backend endpoint exists, document this limitation clearly for the repository owner.

Calls to action should be concrete, for example:

- Ver proyectos
- Conocer nuestros servicios
- Solicitar cotización
- Hablar sobre mi proyecto

Avoid aggressive or misleading urgency.

## 20. Required workflow

### Phase 1 — Audit

Before major edits:

1. inspect the full repository/mirror;
2. inventory content and assets;
3. identify technical constraints;
4. identify what is real content versus HTTrack scaffolding;
5. identify high-value content that must be preserved.

### Phase 2 — Plan

Briefly state:

- proposed architecture;
- chosen technical approach;
- design-system direction;
- portfolio strategy;
- migration risks;
- what will remain static versus what would require backend work.

### Phase 3 — Implement

Implement the redesign rather than only producing a mockup or a written recommendation.

### Phase 4 — QA

Validate at minimum:

- homepage;
- navigation;
- mobile layout;
- desktop layout;
- project listing;
- multiple individual project pages;
- local images;
- internal links;
- console errors;
- keyboard navigation;
- form behavior;
- broken assets;
- basic performance problems.

If there is a test/build/lint setup, run it.

### Phase 5 — Handoff

At completion, report:

- files added;
- files changed;
- files removed;
- how to run the site locally;
- build commands if applicable;
- tests/checks executed;
- known limitations;
- features that still require the original backend or hosting configuration.

## 21. Definition of done

The task is not complete until:

- the site is actually runnable;
- the redesign works on mobile and desktop;
- the company identity is recognizable;
- real project content has been preserved;
- the portfolio is materially easier to use;
- major links/assets are not broken;
- contact information is based on verified source content;
- no fake business claims were introduced;
- no fake backend behavior was introduced;
- the implementation is maintainable;
- the repository owner receives clear run/handoff instructions.

## 22. First response behavior for a new Codex task

When asked to modernize this repository, do not immediately rewrite everything.

Start by inspecting the repository and respond with a short audit and plan. Then proceed with implementation unless the user explicitly asks for analysis only.

When making design decisions, prioritize in this order:

1. real project photography and content;
2. clarity and trust;
3. mobile usability;
4. portfolio discoverability;
5. performance/accessibility;
6. visual polish.

A beautiful landing page that loses the real portfolio is a regression, not an improvement.
